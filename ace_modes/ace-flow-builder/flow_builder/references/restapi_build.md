# ACE Flow Builder - REST API Build Track

This is the authoritative sub-workflow for building **IBM ACE v13 REST APIs** - projects driven by an OpenAPI/Swagger definition, with a `restapi.descriptor`, a builder-generated `gen/<Api>.msgflow`, one subflow per operation, and three error-handler subflows.

**A REST API is NOT a normal message flow.** Do not hand-author a single `<Flow>.msgflow` with an `HTTPInput → Compute → HTTPReply` pipeline for these. The structure, the `.project`, and the ESQL layout are all different. The divergences are spelled out in [§5](#5-divergences-from-normal-flow-generation) - read them before generating.

A complete, verified golden example lives at `example/rest_api/Test_Rest_Api/` in this skill **if present locally** (the folder is gitignored, so it exists only on the machine where it was built). When in doubt about exact bytes, read it if present; otherwise rely on the golden templates in [§4](#4-golden-templates) - they carry the same verified content.

---

## 1. When this track applies

Route here (instead of the normal Build track in `workflow.md`) when the user wants to **expose** an HTTP API rather than process a message:

- "build a REST API", "create an API", "expose these endpoints"
- "I have an OpenAPI spec / Swagger file", "generate flows from this swagger"
- the user describes a set of HTTP **operations** (GET /x, POST /y) with request/response schemas
- the project should be importable under ACE Toolkit's **REST API** project type

If the user just wants a single synchronous HTTP endpoint with no API contract ("hello world HTTP flow", "one POST that does X"), that is the normal HTTP Request-Reply pattern - stay in the normal Build track.

---

## 2. The two-question gate (ask before generating)

REST API builds always start with two questions. Ask both up front, in one batch, alongside the usual flow-name / project-location / integration-server questions.

**Q0 - Complexity gate (decide from-scratch vs hybrid FIRST).** The `gen/<Api>.msgflow` entry flow + `restapi.descriptor` are normally machine-generated by the ACE Toolkit REST API wizard from the spec; hand-authoring them is reliable for a simple API but risks divergence as the spec grows. So assess complexity before generating:
- **Simple → generate from scratch** (the verified path): roughly **≤ 5 operations**, flat/straightforward request & response schemas (little or no nested `$ref`), **no** security/auth schemes, a single resource/tag, standard or stub handlers.
- **Complex → ASK the user first**: **> ~5 operations**, `$ref`-heavy / deeply nested / shared component schemas, **security definitions** (OAuth2 / API keys / scopes), multiple tags/resources, content negotiation / multiple media types, or strict response validation. Ask:
  > "This REST API is on the complex side (\<why: N operations / security defs / nested schemas\>). For complex specs it's usually safer to **generate the scaffold in the ACE Toolkit** (Import → OpenAPI → REST API, which produces `restapi.descriptor` + `gen/<Api>.msgflow`) and then have me **finalize** the per-operation logic - mapping, validation, transformations, handlers - via the skill. Want me to (a) generate from scratch anyway, or (b) go hybrid: you scaffold in Toolkit, I finalize?"
  If the user picks **hybrid**, do NOT generate `restapi.descriptor` + `gen/`; instead author/refine the operation + handler subflows and their ESQL against the user's Toolkit-generated scaffold.

**Q1 - From scratch, or from an existing spec?**
> "Are you starting from an existing **OpenAPI / Swagger** file, or building the API **from scratch**?"
- **Existing spec** → ask for the file path, read it, and drive generation from it. This is the primary, verified path.
- **From scratch** → draft a minimal OpenAPI 3 document from the user's description (paths, methods, request/response schemas), write it as `rest-api.yaml`, confirm it, then converge on the exact same downstream generation. Do not invent a bespoke format - produce a real OpenAPI 3 doc so the generated project matches what Toolkit would produce.

**Q2 - Error-handling pattern for the handlers?**
> "Do your handler subflows need to follow a specific **error-handling pattern or framework** (shared error library, standard fault JSON, logging/audit conventions)? If not, I'll generate **stubs** you can fill in."
- **Yes** → implement that pattern inside the three handler subflows' ESQL.
- **No / not specified** → emit **stubs** (the commented `CopyMessageHeaders` / `CopyEntireMessage` + `RETURN TRUE` template in [§4.6](#46-handler-subflow-esql-stub)).

**Operation subflows hold the business logic.** That is where per-operation processing goes. If the user describes logic for an operation, implement it in `<operation>_Compute.esql`. If nothing is specified for an operation, emit a **stub** (same template as the handlers) and mark it `[CONFIGURE: business logic for <operation>]` in Iterative mode.

## 3. Naming rules (verified against the example)

| Thing | Rule | Example |
|---|---|---|
| Project name | User-supplied. Used as the directory name, `.project` `<name>`, `gen/<name>.msgflow`, and the `<Api>` prefix on handler names. | `Test_Rest_Api` |
| Operation name | The OpenAPI `operationId` if present; otherwise synthesize `<method><PascalCasePath>`. | `GET /hello` → `getHello`; `POST /hello` → `postHello` |
| Operation subflow | `<operation>.subflow` + `<operation>_Compute.esql` | `getHello.subflow`, `getHello_Compute.esql` |
| Handler subflows | `<Api>Input<Type>Handler` for `Type` ∈ {Catch, Failure, Timeout} | `Test_Rest_ApiInputCatchHandler` |
| Handler ESQL | `<Api>Input<Type>Handler_Compute.esql` | `Test_Rest_ApiInputCatchHandler_Compute.esql` |
| `URLSpecifier` | OpenAPI `servers[0].url` path component + `*` | server `https://localhost:8400/testRest/v1` → `/testRest/v1*` |

Note the `Input` infix on handler names - it derives from the HTTP Input node, not the API name alone.

## 4. Golden templates

Replace `<Api>` with the project name, `<op>` with each operation name. Everything else is literal. Indentation/namespaces matter - match exactly.

**Node `location="x,y"` coordinates are cosmetic** - they are canvas positions Toolkit assigns and re-lays-out on open. The fixed values in these templates build and run correctly; you do not need to reproduce the golden example's exact coordinates. (Verified: a project generated from these templates builds identically via `ibmint package` regardless of node positions.) The same goes for trailing whitespace and CR/LF line endings - they do not affect `ibmint package`.

### 4.1 File tree to produce

```
<Api>/
├── .project
├── .settings/
│   └── org.eclipse.core.resources.prefs
├── rest-api.yaml                         (the OpenAPI spec - kept verbatim; see §4.8)
├── restapi.descriptor
├── gen/
│   └── <Api>.msgflow                     (builder-generated; see §5)
├── <op>.subflow                          (one per operation)
├── <op>_Compute.esql                     (one per operation)
├── <Api>InputCatchHandler.subflow
├── <Api>InputCatchHandler_Compute.esql
├── <Api>InputFailureHandler.subflow
├── <Api>InputFailureHandler_Compute.esql
├── <Api>InputTimeoutHandler.subflow
└── <Api>InputTimeoutHandler_Compute.esql
```

### 4.2 `restapi.descriptor`

```xml
<?xml version="1.0" encoding="UTF-8" standalone="yes"?>
<ns2:restapiDescriptor xmlns="http://com.ibm.etools.mft.descriptor.base" xmlns:ns2="http://com.ibm.etools.mft.descriptor.restapi" definitionType="openapi_3" definitionFile="rest-api.yaml" implementation="gen/<Api>.msgflow" https="false" definitionWithExtRef="false" faultFormat="JSON">
    <ns2:operations>
        <ns2:operation name="<op>" implementation="<op>.subflow"/>
        <!-- one <ns2:operation> per operation -->
    </ns2:operations>
    <ns2:errorHandlers>
        <ns2:errorHandler type="CATCH" implementation="<Api>InputCatchHandler.subflow"/>
        <ns2:errorHandler type="FAILURE" implementation="<Api>InputFailureHandler.subflow"/>
        <ns2:errorHandler type="TIMEOUT" implementation="<Api>InputTimeoutHandler.subflow"/>
    </ns2:errorHandlers>
</ns2:restapiDescriptor>
```

- `definitionFile` MUST match the real spec filename on disk (see §4.8).
- `implementation` points at `gen/<Api>.msgflow`.
- `https="false"` unless the user wants TLS at the listener.

### 4.6 Operation / handler ESQL stub

**This is the default for every operation subflow and every handler subflow unless the user specified logic or an error-handling pattern.** Note: **no `BROKER SCHEMA` line**, default schema, file at project root.

```esql


CREATE COMPUTE MODULE <Name>_Compute
	CREATE FUNCTION Main() RETURNS BOOLEAN
	BEGIN
		-- CALL CopyMessageHeaders();
		-- CALL CopyEntireMessage();
		RETURN TRUE;
	END;

	CREATE PROCEDURE CopyMessageHeaders() BEGIN
		DECLARE I INTEGER 1;
		DECLARE J INTEGER;
		SET J = CARDINALITY(InputRoot.*[]);
		WHILE I < J DO
			SET OutputRoot.*[I] = InputRoot.*[I];
			SET I = I + 1;
		END WHILE;
	END;

	CREATE PROCEDURE CopyEntireMessage() BEGIN
		SET OutputRoot = InputRoot;
	END;
END MODULE;
```

`<Name>` is the operation name (`getHello`) or handler name (`<Api>InputCatchHandler`). The file leads with two blank lines and uses tab indentation - that is the Toolkit-emitted form; reproduce it. When implementing real business logic, keep `CREATE COMPUTE MODULE <Name>_Compute` and `Main()`, and use the ESQL patterns library in `workflow.md` §3.2 (build the JSON response, set HTTP status, etc.).

## 5. Divergences from normal-flow generation

These are the points the normal Build track gets wrong for REST APIs. They override `workflow.md` for this track:

1. **ESQL lives at the project root with the default schema.** No `BROKER SCHEMA <X>` line, files NOT under `<project>/<X>/`, and the `computeExpression` URI is `esql://routine/#<Module>.Main` (empty between `/` and `#`). The normal-flow "use a dotted-package `BROKER SCHEMA` under the matching nested folder" rule does **not** apply here.
2. **No `_HandleException.esql` and no `OutTerminal.catch → HandleException` wiring on the input node.** Error handling is the three descriptor-declared handler subflows (CATCH / FAILURE / TIMEOUT), wired from the WSInput's `catch`/`failure`/`timeout` terminals in the generated flow.
3. **The entry flow lives in `gen/` and carries the auto-generated "do not edit" sticky note.** It is derived from the descriptor + spec, not hand-authored business logic.
4. **The `.project` uses the REST API nature + builders** (`com.ibm.etools.mft.restapi.ui.Nature`, `restApiBuilder`, `restApiDefinitionsBuilder`), not the plain two-nature normal-flow `.project`.
5. **`URLSpecifier` comes from the OpenAPI server path + `*`**, and the input node is JSON-domain with `parseQueryString="true"` and `faultFormat="JSON"`.
6. **One subflow + ESQL pair per operation**, plus exactly three handler subflows - not a single Compute module.

- [ ] `restapi.descriptor` exists; its `definitionFile` matches the spec filename on disk; `implementation` = `gen/<Api>.msgflow`.
