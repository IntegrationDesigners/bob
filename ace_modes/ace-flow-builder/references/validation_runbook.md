# ACE Flow Validation Runbook

Loaded by Phase B5 (Post-Build Validation) when the user picks level 2 (build + deploy) or level 3 (build + deploy + run). Contains the per-node-type dependency probes, override-file generation, multi-project staging, mock patterns, scenario template, output verification, credential handling, cleanup, and edge cases.

Phase B5 in `workflow.md` is the **orchestrator**; this runbook is the **how**.

---

## Section 1 - `<FlowName>_LOCAL.properties` overrides

The ACE-native mechanism for redirecting prod URLs / hostnames / proxies to a local mock during validation. Always preferred over manually editing the BAR or hardcoding URLs.

### Convention

`<project>/deploymentDescriptors/<FlowName>_LOCAL.properties`

### Generating the file

1. Parse the `.msgflow` for hardcoded URLs and hostnames in:
   - `ComIbmWSRequest` `URLSpecifier` attribute
   - HTTP Request user-defined properties (UDPs)
   - Any compute-node-set environment variables (look in the matching `.esql`)
2. For each, propose a local-mock override. Default mock URL: `http://localhost:7801`.
3. Show the user the proposed file and ask for confirmation before writing.

### Format

```properties
# Override file generated by Phase B5. Redirects prod URLs to localhost.
# Apply with:
#   ibmint apply overrides <FlowName>_LOCAL.properties \
#       --input-bar-file <FlowName>.bar \
#       --output-bar-file <FlowName>_LOCAL.bar

# Per-flow UDP overrides (one block per flow that needs redirection)
<FlowName>#APIM_Host=http://localhost:7801
<FlowName>#baseURL=http://localhost:7801
<FlowName>#APIM_Proxy=
```

### Applying

```bash
ibmint apply overrides <FlowName>_LOCAL.properties \
    --input-bar-file <FlowName>.bar \
    --output-bar-file <FlowName>_LOCAL.bar
```

The output BAR is what gets staged into `work_dir/run/`.

## Section 2 - Multi-project staging (Windows directory junctions)

When the application references shared libraries and/or a PolicyProject, all projects must be visible to `ibmint package --input-path` in a single scan. Copying duplicates files; junctions reference them.

### Convention

```
<workspace-or-build-dir>/
├── stage/
│   ├── <Application>/        ← junction to the real app project
│   ├── <SharedLib1>/         ← junction to a shared library
│   ├── <SharedLib2>/
│   └── PolicyProject/        ← junction to the policy project
```

### Creating junctions on Windows

```cmd
mklink /J stage\<Application>      C:\Users\<user>\IBM\ACET13\workspace\<Application>
mklink /J stage\<SharedLib1>       C:\Users\<user>\IBM\ACET13\workspace\<SharedLib1>
mklink /J stage\PolicyProject      C:\Users\<user>\IBM\ACET13\workspace\PolicyProject
```

### Detecting which projects to stage

1. Read `<project>/application.descriptor` - `<references>` section lists shared libraries the application depends on.
2. Read `<project>/.project` - sometimes carries additional dependency hints in the `<projects>` section.
3. Read `.msgflow` files for `policyName` / `policyType` attributes that reference an external policy project.
4. If the user has a known PolicyProject (e.g. supplying default MQ policy), include it explicitly.

### Packaging

```bash
ibmint package --input-path stage \
    --output-bar-file <Bundle>.bar \
    --do-not-compile-java
```

`--do-not-compile-java` skips JavaCompute recompilation when only ESQL/`.msgflow` changed. Omit when JavaCompute source has changed.

## Section 3 - PolicyProject for MQ access

Reaching MQ from the IS - especially in CLIENT mode against a Docker QM1 - requires an MQEndpoint policy. Convention: a separate `PolicyProject` deployable that defines the policy.

### Minimal `DefaultMQInsecureLocal` policy

```xml
<?xml version="1.0" encoding="UTF-8"?>
<policies>
  <policy policyType="MQEndpoint" policyName="DefaultMQInsecureLocal" policyTemplate="MQEndpoint">
    <connection>CLIENT</connection>
    <queueManagerHostname>localhost</queueManagerHostname>
    <listenerPortNumber>1414</listenerPortNumber>
    <queueManagerName>QM1</queueManagerName>
    <channelName>INSECURE.APP.SVRCONN</channelName>
    <securityIdentity></securityIdentity>
  </policy>
</policies>
```

### Wiring in `server.conf.yaml`

```yaml
remoteDefaultQueueManager: '{PolicyProject}:DefaultMQInsecureLocal'
```

This top-level key tells the IS that any flow not naming its own policy should reach MQ via `DefaultMQInsecureLocal` from the `PolicyProject`.

**Common mistake - do NOT use these keys**, they aren't recognized in v13:

| Wrong key | What goes wrong |
|---|---|
| `defaultPolicyProject` | Server start fails: *"An unexpected object name 'defaultPolicyProject' was encountered"* |
| `defaultPolicyProjects` | Same error, plural variant. The first MQ-using flow then fails to start with `BIP1388E: Policy ... of type 'MQ' is required for server startup, but is not present` |

The right key is **`remoteDefaultQueueManager`** at the top level, valued as `{PolicyProject}:PolicyName`.

### Where the PolicyProject lives at runtime

**Critical:** the policy project must be present as a **folder** under `<work_dir>/run/`, NOT bundled inside a BAR. Bars load after the MQ Director starts, so even a perfectly-correct policy in the BAR fails IS startup with `BIP1388E`. Stage as:

```
work_dir/run/PolicyProject/
    policy.descriptor
    DefaultMQInsecureLocal.policyxml
    ...
```

The IS scans `run/` for both policy projects (folders) and BAR files; policies load **before** bars and the MQ Director, which is what makes them available at the moment the Director starts.

You can also deploy policy projects the same way you deploy apps and BARs (via `ibmint deploy`) when using a node-managed runtime.

### Credentials

If the channel needs auth, store credentials in the vault keyed to the policy name (see Section 7). Do **not** put credentials in the policy XML.

## Section 4 - `server.conf.yaml` customisation

A local-validation `server.conf.yaml` typically needs:

```yaml
# Default policy project for MQ - TOP-LEVEL key, NOT under a sub-block.
# Format: '{PolicyProject}:PolicyName'.
# Do NOT use defaultPolicyProject / defaultPolicyProjects - see Section 3.
remoteDefaultQueueManager: '{PolicyProject}:DefaultMQInsecureLocal'

# HTTP listener config - MUST be nested under ResourceManagers.
# Putting HTTPConnector at the top level fails with:
#   "An unexpected object name 'HTTPConnector' was encountered"
ResourceManagers:
  HTTPConnector:
    ListenerPort: 7801
    PreserveHTTPMethod: true   # otherwise HEAD requests arrive as GET

  # Optional: route trace + console logging
  JVM:
    jvmSystemProperty: '-Djavax.net.debug=all'
```

Generate this file in `work_dir/server.conf.yaml` before starting `IntegrationServer`. Probe for port collisions (Section 9) and offer alternates.

### Windows-specific: set codepage 1252 before launching SIS

Default Windows console codepage is 65001 (UTF-8). ACE on Windows can't process this and emits `BIP2132E: Invalid codepage '65001' or conversion table 'ibm-65001' missing or invalid` for **every** flow on startup, blocking all of them. Always prefix the launch with `chcp 1252`:

```bat
chcp 1252 && IntegrationServer --work-dir work_dir --name <Server> --console-log
```

Or in a PowerShell-driven session, switch the console first then launch through `cmd /c` with the chcp prefix. The startup script the skill emits for Windows must include this - assume the user's terminal is at 65001 by default.

Linux / WSL launches don't need this.

## Section 5 - MQ definitions via `runmqsc`

Before running, queues and subscriptions must exist on the qmgr.

### Convention

`<project>/mqsc/MQDefs.mqsc` - project-tree convention for queue/sub definitions.

### Minimal example

```mqsc
DEFINE QLOCAL('ADPT.<NAME>.IN') REPLACE
DEFINE QLOCAL('ADPT.<NAME>.OUT') REPLACE
DEFINE QLOCAL('ADPT.<NAME>.RETRY') REPLACE
DEFINE QLOCAL('ADPT.<NAME>.DROP') REPLACE
```

### Applying against a Docker MQ

```bash
docker cp <project>/mqsc/MQDefs.mqsc QM1:/tmp/
docker exec QM1 bash -c "runmqsc QM1 < /tmp/MQDefs.mqsc"
```

### Applying against a local QM (Windows / Linux)

```bash
runmqsc QM1 < <project>/mqsc/MQDefs.mqsc
```

### Generating MQDefs.mqsc when missing

If the project doesn't ship `mqsc/MQDefs.mqsc`, parse the `.msgflow` for:
- `ComIbmMQInput.msgnode` `queueName` attributes
- `ComIbmMQOutput.msgnode` `queueName` attributes
- `OutputLocalEnvironment.Destination.MQ.DestinationData[N].queueName` references in ESQL

Generate a minimal MQDefs.mqsc with `DEFINE QLOCAL` for each. Confirm with the user before running.

## Section 6 - Fixture-driven HTTP mock pattern

A real validation mock is **not** "always 200 OK". It returns different responses per ID/path to drive different flow branches.

### Pattern

The mock listens on `localhost:7801` (or whatever the `_LOCAL.properties` redirect points at) and responds based on the request path/method:

| Request | Response | Drives branch |
|---|---|---|
| `POST /<...>/oauth2/v2.0/token` | `200 {"access_token": "fake-token"}` | OAuth token retrieval |
| `HEAD /Users/00000016123` | `200` | "user exists" → UPDATE branch |
| `HEAD /Users/00000027430` | `404` | "user missing" → CREATE branch |
| `POST /Users` | `201 + Location header` | Create flow |
| `PUT /Users/<id>` | `200` | Update flow |

### Minimal Python `http.server` mock

```python
# mock_server.py - fixture-driven HTTP mock for ACE flow validation
from http.server import BaseHTTPRequestHandler, HTTPServer
import json

# fixture state - different responses per ID
FIXTURES = {
    "00000016123": {"status": 200, "body": {"id": "00000016123", "exists": True}},
    "00000027430": {"status": 404, "body": {"error": "not found"}},
}
SHARED_STATE = {}  # for POST/PUT round-trip tests

class MockHandler(BaseHTTPRequestHandler):
    def _send(self, status, body=None):
        self.send_response(status)
        self.send_header("Content-Type", "application/json")
        self.end_headers()
        if body is not None:
            self.wfile.write(json.dumps(body).encode())

    def do_POST(self):
        if self.path.endswith("/oauth2/v2.0/token"):
            self._send(200, {"access_token": "fake-token", "expires_in": 3600})
            return
        if self.path == "/Users":
            length = int(self.headers.get("Content-Length", 0))
            data = json.loads(self.rfile.read(length)) if length else {}
            SHARED_STATE[data.get("id", "")] = data
            self._send(201, {"id": data.get("id"), "created": True})
            return
        self._send(404)

    def do_HEAD(self):
        # /Users/<id>
        parts = self.path.rstrip("/").split("/")
        if len(parts) >= 3 and parts[1] == "Users":
            user_id = parts[2]
            if user_id in FIXTURES:
                self._send(FIXTURES[user_id]["status"])
            elif user_id in SHARED_STATE:
                self._send(200)  # post-create round trip
            else:
                self._send(404)
            return
        self._send(404)

    def do_PUT(self):
        parts = self.path.rstrip("/").split("/")
        if len(parts) >= 3 and parts[1] == "Users":
            self._send(200, {"id": parts[2], "updated": True})
            return
        self._send(404)

    def log_message(self, format, *args):
        # Quieter: only log non-2xx responses
        if not args or "200" not in str(args[0]):
            super().log_message(format, *args)


if __name__ == "__main__":
    server = HTTPServer(("0.0.0.0", 7801), MockHandler)
    print("Mock listening on :7801")
    server.serve_forever()
```

Run with: `python mock_server.py`. The fixture IDs and branch mappings come from the flow's design - adapt per flow.

### Resetting state

If shared state needs to be clean between runs, restart the mock (`Ctrl-C` and re-run). Document this requirement in the flow's `TESTING.md`.

## Section 7 - Credential handling (vault)

The ACE vault is the **only** mechanism Phase B5 should suggest. `mqsisetdbparms` is the IIB-era legacy command - never recommend it.

### About the vault

For a single independent integration server, the vault is **created implicitly** the first time you call `ibmint set credential --work-directory <dir>` against that work directory - you don't need a separate "create" step.

`ibmint create vault` is for **external directory vaults** that are shared across multiple servers/nodes. The syntax for that is different (positional path + optional key flag); skip it for single-server validation.

### Add or update a credential

```bash
ibmint set credential --work-directory <work_dir> \
    --credential-type <mq|jdbc|http|kafka|smtp|oauth|...> \
    --credential-name <identifier-matching-the-policy-or-flow-binding> \
    --vault-key <key>
```

Notes on the actual command syntax (verified against `ibmint set credential --help` on ACE 13.0.7.0):
- The command name is **singular** (`set credential`), the list and bulk-import commands use plural - easy to get wrong, IBM's choice
- `--credential-type` and `--credential-name` are the full flag names (not `--type` / `--name`)
- `--work-directory` is the connection spec for an independent integration server; alternatives include `--integration-node <name>`, `--admin-host <host> --admin-port <port>`, `--integration-connection-file`, and `--admin-uri <URI>` for remote nodes/servers
- `--vault-key <key>` supplies the passphrase; `--vaultrc-location <dir>` reads it from a `.mqsivaultrc` file instead

Run `ibmint display credential-types --show-auth-types` to see the full list of valid types and the properties each one needs.

Common types and naming:

| Type | `--credential-name` value |
|---|---|
| `mq` | The qmgr name OR the MQEndpoint policy name (e.g. `DefaultMQInsecureLocal`) |
| `jdbc` | The JDBC provider name |
| `http` | The HTTP Request node's security identity name |
| `kafka` | The Kafka policy name |
| `oauth` | The OAuth policy / security profile name |

### Pass the vault key to the runtime

Two equivalent options at server start:

```bash
# Option A - flag
IntegrationServer --work-dir work_dir --name <Server> --console-log --vault-key <key>

# Option B - environment variable (read by the IntegrationServer process)
export MQSI_VAULT_KEY=<key>
IntegrationServer --work-dir work_dir --name <Server> --console-log
```

### Inspect / remove

```bash
# List what's set (values masked) - note: this command uses the plural "credentials"
ibmint display credentials --work-directory <work_dir> --vault-key <key>

# Optionally filter by type or name:
ibmint display credentials --work-directory <work_dir> --vault-key <key> \
    --credential-type mq

# Remove a credential - note: the verb is "unset", and singular "credential"
ibmint unset credential --work-directory <work_dir> \
    --credential-type mq --credential-name <name> --vault-key <key>
```

**Command-naming gotchas in v13** (verified via `ibmint help` against ACE 13.0.7.0):
- The verb for adding is `set credential` (singular). For removing it's `unset credential` (different verb, also singular).
- The verb for listing is `display credentials` (different verb again, plural here only). `report credentials` does not exist.
- See `ibmint help` for the full command tree.

### Storage rules

- **Never** persist credentials to `flow_state.md`, `TESTING.md`, the project, the BAR, `_LOCAL.properties`, or anywhere on disk under the project tree
- The vault key (passphrase) is the only secret the user manages directly
- For Docker MQ specifically: the qmgr's own auth (e.g. `app` / `passw0rd` defined in `compose.yaml`) is owned by the compose file. The IS-to-qmgr connection creds the *flow* needs go in the vault on the IS work_dir.

### Production note

Same path. Production deploys use the vault. No "ok for local but not prod" or "use mqsisetdbparms in pinch" - the vault is the only recommended mechanism.

## Section 8 - Test scenarios template (S1 / S2 / S3)

Every Level-3 validation produces three scenarios. Adapt per flow.

### S1 - Mock smoke test (no MQ required)

Goal: confirm the mock fixtures behave as expected before running the flow.

Hit the mock directly with `curl`. For an HTTP-downstream flow with the fixture mock from Section 6:

```bash
# Token endpoint
curl -s -X POST http://localhost:7801/<...>/oauth2/v2.0/token

# Fixture HEAD checks
curl -s -o /dev/null -w "%{http_code}\n" -X HEAD http://localhost:7801/Users/00000016123  # → 200
curl -s -o /dev/null -w "%{http_code}\n" -X HEAD http://localhost:7801/Users/00000027430  # → 404

# POST + HEAD round-trip via shared state
curl -s -X POST http://localhost:7801/Users \
     -H 'Content-Type: application/json' \
     -d '{"id":"99999","firstname":"Test","lastname":"User"}'
curl -s -o /dev/null -w "%{http_code}\n" -X HEAD http://localhost:7801/Users/99999  # → 200
```

If any of these don't match expectations, fix the mock before moving to S2.

### S2 - Full pipeline

Goal: drop a sample input through the flow's real entry point and watch it traverse the full path.

Per node type:

| Input node | Command |
|---|---|
| `ComIbmWSInput` (HTTP) | `curl -X POST http://localhost:7801/<path> -H 'Content-Type: application/json' -d @sample.json` |
| `ComIbmMQInput` (MQ) | See **`amqsput` per-line trap** below - never feed multi-line files directly. Docker: `tr -d '\n' < sample.json \| docker exec -i QM1 /opt/mqm/samp/bin/amqsput <queueName> QM1`. Local: `tr -d '\n' < sample.json \| amqsput <queueName> QM1`. |
| `ComIbmFileInput` | `cp sample.xml \\netwerk\dfs\<inputDirectory>\` (or Windows-equivalent) |
| `ComIbmTimeoutNotification` (Automatic) | none - wait for the configured `timeoutInterval` and observe |

Watch the IS console for the expected `BIP*` codes and log-status strings (Section 10).

### S3 - Exception paths

Goal: confirm the flow handles bad input gracefully - error/DROP branch routes, doesn't crash.

For a typical MQ-input flow:

- Drop a message with a missing required field → expect `WARN status="missing-<field>"` log + DROP terminal
- Drop a message with an invalid Action header → expect `WARN status="invalid-action"` log + DROP terminal
- Drop a message that exceeds size limits → expect graceful rejection, not crash

Adapt the cases per flow. Two scenarios per flow is usually enough.

### `amqsput` per-line trap

`amqsput` reads STDIN and **PUTs each newline-separated line as a separate MQ message**. Feeding a multi-line JSON or XML file directly fragments it across many tiny messages, which is almost never what you want and floods the input queue with unparseable junk.

**Always flatten newlines before piping into `amqsput`:**

```bash
# Single message - multi-line JSON flattened
tr -d '\n' < sample.json | amqsput <queueName> <QMGR>

# Same for Docker
tr -d '\n' < sample.json | docker exec -i QM1 /opt/mqm/samp/bin/amqsput <queueName> QM1
```

If the message body genuinely needs newlines (e.g. CSV, multi-line text), use `mqput`/`mqput2` from the IBM MQ samples instead - they read the whole STDIN as one message - or write the file to a one-shot named queue via `mqsim` / a small script. Don't try to escape newlines in `amqsput` input; it doesn't honor escapes.

This trap surfaces during S2 every time the test data file is JSON-pretty-printed. The fix is the `tr -d '\n'` prefix.

## Section 9 - Output verification by node type

| Output node | Verification command |
|---|---|
| `ComIbmWSReply` (HTTP) | Capture the `curl` response from S2; assert status code + body shape |
| `ComIbmMQOutput` (MQ) | `docker exec -i QM1 /opt/mqm/samp/bin/amqsget <queueName> QM1` (Docker) or `amqsget <queueName> QM1`. For inspection without consuming: `amqsbcg <queueName> QM1` |
| `ComIbmFileOutput` | `ls <outputDirectory>` after waiting up to 30s; `cat` the produced file to verify contents |
| `ComIbmWSRequest` (downstream call) | Mock log captures the call; verify in mock stdout |
| Internal queues (RETRY / DROP) | `amqsget` to drain; assert the right messages landed where expected |

### Default timeout

30 seconds per message. Configurable per call. If timeout expires without expected output, declare failure.

### Port-collision handling

Probe `7600` (admin REST), `7800` (default HTTP), `7801` (mock):

```bash
# Linux / WSL
ss -tnlp | grep -E ':(7600|7800|7801)\b'
# Windows
netstat -ano | findstr "7600 7800 7801"
```

If a port is occupied, offer the next free port (`7602`, `7802`, `7803`...) and update `server.conf.yaml` accordingly.

## Section 10 - "What to watch for" - expected console output

### IntegrationServer startup (good signs)

| BIP code | Meaning |
|---|---|
| `BIP9332I` | Application has been reloaded successfully |
| `BIP2269I` | Application has been deployed |
| `BIP1145I` | HTTP listener started on port N |

### Application errors (action required)

| BIP code | Meaning | Likely cause |
|---|---|---|
| `BIP1239E` | Application references a shared library that is not deployed | Missing project in stage/, or shared lib not in BAR |
| `BIP2111` | Process abend | Crash - collect for support, don't try to validate further |
| `BIP2322E` | SSL handshake failure | TLS / cert / cipher issue |
| `BIP2420E` | ESQL data type mismatch | Compile-level bug, fix before re-validating |
| `BIP3108` | LIL load failure | UDN incompatibility |

### Per-flow log-status strings (convention)

Generated flows that follow this skill's patterns log structured status strings via the LoggingLibrary (or equivalent). Watch for:

- `status="head-user"` / `"build-update"` / `"build-create"` - expected progress markers in user-sync flows
- `status="missing-<field>"` / `"invalid-action"` - expected error markers in S3 exception runs
- Any `status` containing `"error"` or `"fatal"` - investigate before declaring PASS

Per-flow, the skill should know what status strings are expected (from the generated ESQL). Compose the watch-list during B5.

## Section 11 - Edge cases

### Timer / scheduled flows

No input message to push. Validation = "did the timer fire and did the downstream activity happen within N timer cycles?"

- For `ComIbmTimeoutNotification` Automatic mode: wait `timeoutInterval × 2` seconds, then check the downstream output. If nothing → fail.
- For Controlled mode (paired with `ComIbmTimeoutControl`): drive a message through the upstream flow that schedules the timer, then wait the scheduled delay + small margin, then check the downstream output.

### Pure pub/sub flows

The subscriber must be running before the publisher fires, otherwise the message is lost.

- Spin up a subscriber first: `docker exec -i QM1 /opt/mqm/samp/bin/amqssub <topicString> QM1` (in a separate terminal or background process)
- Then publish the test message via the flow's input

### Multiple input sources on one flow

If the flow has, say, both an `ComIbmWSInput` and a `ComIbmTimeoutNotification`, ask the user which input path to validate. Don't try to exercise both in one S2.

### Shared libraries and PolicyProject (covered in Section 2)

Detection is automatic from `application.descriptor` `<references>`. If a referenced lib isn't in the staging set, fail clearly with a pointer to mklink commands.

### Idempotent re-run

Re-running B5 against the same `work_dir`:
- Standalone server: stop it (`Ctrl-C` or `taskkill` on Windows), update the BAR in `work_dir/run/`, restart. The IS reloads on startup.
- Node-managed: `ibmint deploy` against an existing app overwrites it. No teardown needed.

### Cleanup / teardown

At the end of validation, ask:
> "Validation complete. Cleanup options:
> 1. **leave running** - the standalone server keeps running for further iteration (recommended for Iterative mode)
> 2. **stop server only** - kill the IntegrationServer; leave Docker MQ running (you may have other flows using it)
> 3. **stop everything** - kill server, `docker compose down` for the MQ container, remove temp work_dir
> 4. **leave running and stop the mock** - the mock has shared state that should reset"

For Docker MQ specifically: only run `docker compose down` if the user owns the compose file. If the user spun up MQ via a shared compose, leave it.

## Section 12 - Output to `TESTING.md`

Use the `TESTING_template.md` template. Fill in:

- **What's under test** - one paragraph describing the flow path being validated, including the redirect target (mock URL) so the reader knows what's being substituted
- **Components** - the runtime ingredients: Docker MQ + channel + compose file path; PolicyProject; mock; `_LOCAL.properties` overrides
- **Build + deploy** - the exact command sequence ready to copy-paste, including queue setup, staging, package, override application, server start
- **Test scenarios** - S1 / S2 / S3 with concrete commands and inputs (the actual `curl` / `amqsput` invocations that ran)
- **What to watch for** - per-scenario list of expected `BIP*` codes / log-status strings (from Section 10)
- **Cleanup** - `docker compose down`, stop server, remove temp dirs (per the user's choice in Section 11)
- **Things this test cannot prove** - explicit limitations list. Always include: real auth flow (vs the canned token), real downstream verbose error bodies, network-partition / retry-policy behaviour (the mock always answers), production proxy + TLS configuration. Adapt per flow.

Write to `<project>/TESTING.md`. Overwrite if it exists (Iterative re-validation produces a fresh document; the historical record lives in `flow_state.md`'s "Validation Results" section).
